# Исследование публичных сведений об утечках

## Итоговый групповой проект по блокчейну

Тема: **«Анализ и кластеризация инцидентов утечки данных для оценки применимости блокчейн-технологий в защите информации»**.

Готовые материалы: `deliverables/Report.docx` (отчёт), `deliverables/Presentation.pptx` (презентация), `DEFENSE_GUIDE.md` (подготовка к защите) и `report.html` (визуальный результат). Полный запуск: `source("run_project.R", encoding="UTF-8")` в RStudio из папки проекта.

Выполнены анализ, кластеризация, сравнение архитектур по первоисточникам и синтетический опыт с целостностью журнала. Блокчейн-сеть и смарт-контракт не развёрнуты: согласованная тема посвящена оценке применимости. Локальная хеш-цепочка не выдаётся за блокчейн.

`project_materials/comparison.csv` сравнивает БД, журнал, цифровую подпись и permissioned-блокчейн. `scenarios.csv` связывает задачи защиты с мерами и ограничениями. Источники и дата проверки — в `blockchain_assessment.json`. `integrity_demo.py` создаёт результаты в `results_integrity/`; его события синтетические.

Для повторного полного запуска нужны R с пакетом `cluster` и Python 3.10+ без дополнительных библиотек. Если Python не найден, R показывает сохранённый опыт и сообщает об этом. Интернет нужен только для нового скачивания VCDB/HIBP. Повторная сборка DOCX требует python-docx (`project_materials/build_report.py`); для запуска исследования он не нужен. Готовые DOCX/PPTX входят в архив.

**Основной вариант проекта — анализ и кластеризация сценариев утечек.** Откройте `OpenBaseSearch.Rproj` в RStudio и выполните `source("run_project.R", encoding = "UTF-8")`: анализ запустится, а результат автоматически откроется в браузере. Начните с [README_CLUSTERING.md](../README_CLUSTERING.md). Подготовленные данные: `data_clusters/`; результаты: `results_clusters/` и `report.html`. Целевая переменная не нужна.

## Расширенный набор для исследования механизмов: VCDB

Начните с этого набора, если нужны подробности о механизмах инцидентов. В проект добавлен реальный снимок [VERIS Community Database](https://github.com/vz-risk/VCDB) на commit `f6f98c00f66ab35f5b49977a5852ce94a5bb31d1` от 30 сентября 2026 года. Это **10 047 карточек**, 32 столбца основной таблицы и 80 различных структурированных полей в связанной таблице. Не все поля заполнены у каждой карточки. По размеру это обычный исследовательский датасет, который помещается в память ноутбука, а не Big Data в техническом смысле.

Данные уже лежат в `data_vcdb/`, результаты — в `results_vcdb/`. Для анализа интернет не нужен:

```r
source("analysis_vcdb.R")
```

Рабочий каталог RStudio должен быть папкой проекта. Дополнительные пакеты не требуются. Скрипт вызывает вспомогательный `vcdb_report.R` и создаёт русскоязычный отчёт `results_vcdb/report_ru.txt`.

Для повторной загрузки точно того же снимка:

```sh
python3 collect_vcdb.py
```

Для офлайн-импорта официального ZIP репозитория: `python3 collect_vcdb.py --archive /path/to/vcdb.zip`. Другую версию можно задать полным SHA через `--commit`. База заменяется транзакционно, CSV записываются после неё; не запускайте два импорта в один каталог одновременно. При ошибке записи CSV повторите импорт. Архив источника не исполняется и не распаковывается в рабочий каталог.

### Структура данных

| Файл | Содержание |
|---|---|
| `incidents.csv` | Одна строка на карточку: организация, страна, отрасль, год/месяц/день, объём раскрытых записей, статус, уверенность источника, длительность обнаружения и сдерживания, категории действий, ссылки |
| `actions.csv` | 46 347 строк: зарегистрированные категории, разновидности, векторы, цели действий, результаты и CVE; связаны через `record_id` |
| `features.csv` | 197 553 значения: действия, участники и мотивы, активы, нарушения конфиденциальности/целостности/доступности, сроки, обнаружение, последствия |
| `field_coverage.csv` | Список 80 полей и количество карточек, где поле присутствует или известно |
| `vcdb.sqlite` | Те же три связанные таблицы для SQL-запросов |
| `manifest.json` | Версия, SHA-256 архива, время сбора и описание преобразований |

Строки `features.csv` и `actions.csv` — характеристики исходных карточек, **не дополнительные независимые инциденты**. Мы не увеличивали датасет синтетическими данными. Подробные публичные описания доступны по `reference` и `source_url`; свободные заметки и имена участников не копируются в таблицу признаков.

В `features.csv` поле `path` сохраняет индексы массивов, например `asset.assets[0].variety`. `field` объединяет одинаковые типы полей, например `asset.assets[].variety`. `value_json` хранит исходный тип JSON; это строка JSON, число, логическое значение или null. Для простого анализа пользуйтесь `incidents.csv` и `actions.csv`; для сложных свойств соединяйте по `record_id` и сохраняйте индексы связанных элементов.

`industry` — код отрасли из источника: загружайте его как текст. `countries` — JSON-массив кодов стран. Год, месяц и день сохраняются отдельно: неизвестные части даты не выдумываются. Длительности сохраняются с исходными единицами; месяцы и годы не переводятся автоматически в точное число дней. `action_* = 1` означает зарегистрированное действие; пустое значение означает отсутствие записи о нём, а не доказанное отсутствие действия.

### Качество и результаты

В снимке 67 карточек с повторяющимися `incident_id`, иногда у разных организаций. Это коллизии ID, а не доказанные дубликаты. Ключ `record_id` взят из имени файла; ни один из этих случаев не объединяется автоматически. Уникальность реальных событий не гарантируется даже при разных идентификаторах.

Основная выборка — 6911 карточек с `security_incident = Confirmed` и `data_disclosure = Yes`, без статуса `Ineligible` и без коллизий ID. Результаты дополнительно сравниваются с выборкой, включающей коллизии, без специально отобранных `phidbr`/`priority`, и только со статусами `Reviewed`/`Finalized`. Сравнение по годам и отраслям показывает влияние фильтра ID.

Каталог `validated` — название раздела репозитория, а не гарантия проверки всех утверждений. Почти половина исходных карточек имеет статус `First pass`. `confidence` — оценка источника, не наша независимая оценка.

Действия VERIS — наблюдаемые механизмы и способствующие факторы, а не единая доказанная первопричина. В карточке может быть несколько действий. Пропуски и `Unknown` нужно анализировать отдельно. Объём записей не равен числу людей. Не суммируйте `data_total` после соединения с многозначными признаками: получите повторный счёт.

VCDB отражает публично описанные случаи и особенности отбора; в том числе есть целевой отбор healthcare и priority. Это не репрезентативная выборка всех организаций. Частоты по отраслям не являются вероятностями взлома. HIBP и VCDB анализируются отдельно: суммировать их как независимые события нельзя из-за возможного пересечения.

Производные данные VCDB, таблицы и графики распространяются на условиях **CC BY-SA 4.0**, с атрибуцией VERIS Community Database, vz-risk and contributors. Полный текст сохранён в `data_vcdb/LICENSE-VCDB.txt`; список преобразований — в `manifest.json`. Документация классификации: [actions](https://verisframework.org/actions.html), [actors](https://verisframework.org/actors.html), [assets](https://verisframework.org/assets.html), [attributes](https://verisframework.org/attributes.html).

## Дополнительный каталог HIBP

Python 3.10+ собирает **метаданные инцидентов** из [Have I Been Pwned](https://haveibeenpwned.com/). Программа не ищет людей и не скачивает базы персональных данных. Это исследование каталога одного источника, а не поисковик по всему интернету.

## Запуск

В терминале из каталога проекта:

```sh
python3 collect.py
```

Сторонние Python-библиотеки и ключ для публичного каталога не нужны. Требуется интернет. Документация источника: https://haveibeenpwned.com/API/v3#AllBreaches . При ограничении запросов программа выведет ошибку; повторите позже.

Результаты в `data/`:

- `breaches.sqlite`: база с таблицами `breaches` и `data_classes`, связанными по `name`.
- `breaches.csv`: название сервиса, домен, даты, число адресов, флаги качества, ссылка и время сбора UTC.
- `data_classes.csv`: категории данных для каждого инцидента; сами данные людей отсутствуют.
- `source.json`: источник, лицензия и время сбора.

Повторный запуск заменяет текущий снимок, не добавляя дубликаты. Для сохранения истории используйте `--out data_YYYY_MM_DD`. SQLite обновляется транзакционно; файлы экспорта создаются после записи базы. При ошибке экспорта повторите запуск. Не запускайте два сборщика одновременно в один каталог.

## Анализ в RStudio

Откройте `analysis.R`, установите рабочий каталог R в папку проекта и выполните:

```r
source("analysis.R")
```

Либо в терминале: `Rscript analysis.R`. Дополнительные пакеты R не нужны. Для анализа используется `data/`; если собирали в другой каталог, измените пути в начале скрипта.

В `results/` появятся таблицы по годам и категориям данных и два PNG-графика. Основная выборка включает подтверждённые инциденты, исключая сфабрикованные записи, списки рассылки и источники из вредоносных программ. Записи с неизвестными флагами также исключаются.

## Интерпретация и предложения для проекта

Исследовательский вопрос: «Какие категории данных чаще встречаются в подтверждённых инцидентах каталога и какие меры уменьшают последствия их компрометации?»

`pwn_count` — число email-адресов, загруженных HIBP для данного инцидента. Сумма по инцидентам содержит повторы и не измеряет число уникальных пострадавших. Категории данных пересекаются, их доли не обязаны давать 100%.

Дата утечки может быть приблизительной. `added_date` — дата добавления в HIBP, а не дата обнаружения. Каталог неполон и не является случайной выборкой всех сервисов. График по годам показывает состав каталога: он не доказывает рост риска; последний год неполный, старые утечки могут добавляться позже. Причины взлома, способ хранения паролей и эффективность защиты по этим полям установить нельзя.

Для обсуждения решений можно предложить проверяемые гипотезы:

- Для последствий компрометации паролей: уникальные пароли, менеджер паролей, passkeys/MFA; на стороне сервиса — стойкое хеширование паролей и отзыв сессий при инциденте.
- Для утечек контактов: минимизация собираемых данных, ограничение сроков хранения и обучение распознаванию адресного фишинга.
- Для больших объёмов раскрытия: минимальные права доступа, разделение хранилищ, контроль массового экспорта и план реагирования.

Это направления для отдельной оценки, а не доказанные выводы о конкретных сервисах. Проверять эффективность можно на синтетических данных и учебном стенде. В отчёте отделяйте наблюдения от гипотез и указывайте дату снимка, фильтры и ограничения.

Данные: [Have I Been Pwned](https://haveibeenpwned.com/), [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/). Сохраняйте атрибуцию в отчёте и на графиках. Экспорт преобразует структуру данных, анализ фильтрует и агрегирует записи. CSV предназначены для импорта в R; не исполняйте текстовые поля как формулы в табличных редакторах.

Проверка сборщика: `python3 -m unittest -v`.
